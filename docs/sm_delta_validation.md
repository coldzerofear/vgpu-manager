# delta 控制器重写验证报告（v13 战役）

对 `library/include/sm_delta.h` 中 `sm_delta_step()` 的全谱系仿真验证：新算法
对旧公式（HAMi-core 同源的 `sm²·thread·diff/2560` 步进，#274 病灶）在
**33000 个闭环场景中稳态精度与锯齿零负格**，冷启动双侧误差最差回退 1.4 个
利用率点（局限于 target≥74、旧公式"灌满到 100%恰好接近目标"的格）。
断言已固化为 CI 测试 `library/test/nogpu/test_delta_campaign.c`。

> **2026-10 更新（v14 见第 7 节；v15 基于消耗观测的削减见第 8 节）**：种子从 pool·5/81920 细化为 pool·5/1310720，
> 并新增"饥饿零读数逃逸"与"1-token 微调下限"两条规则，修掉了 v13 在长 kernel
> 负载下的 bang-bang（HAMi-core #360 同源）。代际战役
> `test_delta_gen_campaign.c` 以冻结的 v13 为基线、在宽 5 个数量级的负载范围上验收。

> 结论先行：新算法在稳态 MAE 上 31223 胜 / 1777 平 / **0 负**（误差聚合
> 1442937 → 175684，降低 8.2 倍）；p95 锯齿 27575 胜 / 5425 平 / **0 负**；
> 冷启动（双侧 MAE，前 300 tick）20935 胜 / 11908 平 / 157 负，负格全部
> ≤1.4 个点。仿真内数字；真机消融（`test/ablation`）仍是最终验收门。

## 1. 为什么重写

HAMi-core issue #274：旧步进 `sm²·thread·diff/2560` 随 SM 数平方增长，而令
牌池 `total = thread/SM × SM数 × 32` 只随 SM 线性增长。步进占池比 ∝ SM 数：

| 卡 | SM | 每 tick 步进占池比（diff=5 时） |
|---|---|---|
| MIG 1g 切片 | 7-14 | ~0.4-0.9% |
| RTX 4080 | 76 | ~4.6% |
| H100 | 132 | ~8.1% |
| 188 SM 级 | 188 | ~11.5%（diff 大时 >20%） |

大卡上桶在一秒内被灌满并钉死，限额从未生效——"大卡限不住"。仿真复现：
188 SM、hard_core=50、轻负载时旧公式平均利用率 **99.8%**（目标 50）。

进一步的发现（本轮仿真最重要的洞察）：**钉死的判据是步进"粒度"而非"幅度"
——只要最小步进大于负载每 tick 的消耗量，桶必然溢出**。消耗量是负载属性
而非卡属性，因此任何绝对值下限（包括线性化的 pool/N 下限）都是灌桶机制本
身。唯一在目标点自适应等于消耗量的量是 share 自己——这是 v13 乘性核心
`share·err/(damp·u)` 的由来。

### 2.2 负载与延迟

- 负载强度 R ∈ {pool/1500, pool/150, pool/15}（每 tick 消耗）：分别对应
  #274 描述的"几分钟才耗尽池"的轻网格、中等负载、重负载（15 tick 吞干全池）。
- 反馈延迟 ∈ {2, 4} tick：NVML 利用率窗口 + share 生效滞后。控制器只能看
  到延迟后的利用率——这是所有失稳模式的放大器。
- 闭环模型与 watcher 实现同构：桶每 tick 加 share（钳位于池容量）、负载最
  多取 R、util = 取到/R、控制器读延迟 util 后更新 share。故意苛刻（桶空时
  util 瞬时坍塌、离散 tick），绝对数字偏悲观，但新旧同受其苦，对比成立。

### 2.3 四维指标

1. **稳态 MAE**：预热后 3000 tick 的 |util−target| 均值——限得准不准。
2. **p95 锯齿**：稳态偏差分布的 95 分位——会不会频繁出现大锯齿。
3. **冷启动双侧 MAE**（前 300 tick）：爬得快不快，**且不以冲破限额为代价**。
   单侧"欠供"指标被弃用：旧公式在小目标格"赢"它的方式是灌到 100% 利用率
   ——用违反限额换吞吐不是胜利，双侧指标对这种违规定价。
4. **鲁棒性场景**（在 `test_delta_step.c` 中单测断言）：4/6-tick 延迟、
   轻→重负载中途切换、冷启动吞吐欠供预算。

## 4. v13 算法要点（每条都对应一个仿真暴露的失败）

| 机制 | 回答的失败 |
|---|---|
| 池相对、share 比例核心 `share·err/(damp·u)`，damp=6 | #274 的 sm² 灌桶；damp<6 在 6-tick 延迟下复利爆炸 |
| 种子 seed = total·5/81920 ≥ 1（v14 改为 /1310720，见第 7 节） | share=0 死锁；粒度低于轻网格消耗率（钉死判据） |
| 一次性 boot 跳升 total·u/6400 | 旧公式唯一真优势（首 tick 直达）；一次性故不参与振荡 |
| 饥饿阻尼 4（桶空时） | 中途重负载恢复慢；damp=2 在 6-tick 延迟爆炸（3→25+） |
| 平滑抗积分 `max(share/(share+bucket), err/100)` | 高目标回撤过狠引发下一次凹陷；硬带边界追逐（worst 格在带边游走） |
| 紧急下限 total·err/(u·64)，门控 err≥5 且 util>2u | 小限额血崩保护；门控防个位数目标的整数抖动误触 |
| u≥100 直通全池 | 100% 限额即无限额，控制器不应介入 |

淘汰路线的教训（详见头文件注释）：绝对步进下限本身就是灌桶机制（divisor
从 16384 扫到 163840 都改变不了钉死）；线性化 `pool/1024` 锚定 4080 在轻载
区同样钉死；远误差加速（damp 2 当 diff·2>u）在 6-tick 延迟下 MAE 3→45。

## 7. v14 代际战役（2026-10）

### 7.1 v13 漏掉了什么

v13 战役只扫了三档负载（每 tick 消耗 pool/1500、/150、/15）。**一个 tick 是一次
控制器周期，即 100 ms**（watcher 对每张卡每 100 ms 跑一次控制器；`TIME_TICK` 的
10 ms 只是 rate_limiter 的退避睡眠）。真实负载的消耗由它发射的 kernel 决定；按 grid
计费时，一个以 tpb 线程/block 填满 GPU、每波 wave_us 微秒的 kernel 在 100% 利用率下：

    R / pool = (100000 / wave_us) × occupancy / (32 × tpb)   （每 100 ms 周期）

与卡无关。10 ms 的大 GEMM（tpb=1024）落在 **pool/3277**，100 ms 级 kernel 落在
pool/32768。v13 的种子 pool/16384 是 10 ms GEMM 全部需求的 1/5，粒度太粗、无法稳住：
H100 限额 50 时 MAE 22.5、p95 50（bang-bang，即 HAMi-core #360），v14 为 1.8、4。
而且硬件越新（SM 越多），同一个小 kernel 的 occupancy 越低，R/pool 越往轻端移。

> 更正（2026-10-23）：本节初版把 tick 当成 10 ms，换算系数错了 10 倍（写成
> "10 ms GEMM = pool/32768、种子是其需求的 2 倍"）。战役本身以 R/pool 为轴，不依赖
> 物理单位，验收结论不受影响；上面已按真实周期重算。

### 7.2 战役设计

| 轴 | 取值 |
|---|---|
| 卡 | 64 款（51 种不同 sm×th 形状）：Pascal→Blackwell 主流与顶级、A2/L20/H100-PCIe/RTX PRO 6000、MIG 1g 切片、合成未来卡 256/384×2048、512/1024×4096 |
| 负载 | R/pool 对数 4 点/十倍程覆盖 [1e-7, 2]，另加 v13 三档；R 为整数 token，下限 1 |
| 限额 / 延迟 | 1-99 / 2、4 tick |
| 起点 | 空桶（与 `g_dev_hot` 零初始化一致） |
| 基线 | v13 逐字冻结副本（含全部常量），原参数自比 0 胜 0 负以证明副本一致 |

验收（代际契约）：

- **v13 三档负载**：沿用逐格判据——稳态 MAE ≤+0.5、p95 ≤+1、冷启动 ≤+1.5，任何格。
- **宽域**：按"负载十倍程 × 限额段（1-9/10-49/50-89/90-99）"分区，每区三项均值
  不劣于 v13（容差 0.05 点）；且任何单格不超过硬上限（稳态 +1.0、p95 +2、冷启动 +2.0）。

为什么宽域不用逐格：两代都有整数量化极限环（1% 利用率分辨率 × 整 token 桶），
在孤立负载点上时有时无。负载轴采样足够密，就必然有样本落在新代的环、旧代的
静点上。例如 u=99、4-tick 延迟：5% 步长细扫 R/pool 0.1-1，新代在 6 款卡上平均 MAE
都低 4-8 倍（0.31→0.04-0.10），但个别负载点读到 0.06→0.6。调参追这些点只会把环挪到
别的负载上。分区均值兜住系统性回退，单格上限兜住孤立回退。

### 7.3 v14 的三处改动

| 改动 | 回答的失败 | 被证伪的替代 |
|---|---|---|
| 种子 pool·5/1310720（≈ pool/262144，GEMM 消耗的 1/8） | #360：种子 > 每 tick 消耗 → bang-bang | 只改除数：小卡残留 400+ 格（下一行的死区），冷启动 600+ 格（第三行） |
| 砍侧 1-token 下限（仅 bucket < share 时） | 小 share 近目标时两项砍量都截断为 0，util 永久停在限额上方 1-4 点（v13 也有，靠粗种子碰巧落近） | 下限=seed：涨 seed/砍 1 不对称时锯齿更大；不加 backlog 门控：排空期把 share 磨到 0，冷启动 1000+ 格 |
| 饥饿零读数逃逸：util=0 且桶空时涨步 ≥ √(2·seed·share) | 细种子下 boot 过冲排空后 share 塌到近 0，线性爬升太慢（冷启动回退） | 池相对绝对 kick：轻端 #360 复现（3000+ 格）；门控 kick：下行穿越被误判为"已收敛"；翻倍/降阻尼：延迟下极限环（2 万+ 格） |

√(2·seed·share) 就是"种子每 tick 再加一个种子"的稳态等价：平方增长而非指数，
share 超过 32·seed 后自然让位给比例项；全程不引入任何池相对的绝对量。

## 8. v15：基于消耗观测的削减（2026-10，两条路径）

### 8.1 问题：灌桶

桶的上限是整个池。share 一旦高于负载的实际消耗（轻负载上的 boot 跳升、重负载中途
变轻、突发结束），多出的 token 就在桶里积压，最多积到一整个池；积压排空之前 util
恒为 100，与 share 无关。限额 ≥50 时 util 不可能超过 2 倍目标，应急下调（util > 2u）
永不触发，只剩温和下调，轻负载上要几十秒到几分钟。v13/v14 都有。

### 8.2 做法

util 是延迟且看不见 share 的信号；桶能说出 util 说不出的事：

    consumed = mark − bucket

mark 是控制器上次读到的桶值加上该周期 winner 施加的每一次改动（drain、补桶），所以
consumed 恰是全容器自那次读数以来发射的 token 数。当上个周期**供给大于消耗**
（consumed < share）且 util 明显超限时，`consumed·u/util` 就是本该维持目标的 share，
桶里的积压按定义是多余的：share 封顶到它，并清空积压（`sm_delta_observe`）。

门控（每条都对应仿真里无门控版本的一个失败）：

| 门控 | 防止的失败 |
|---|---|
| consumed ≥ 100 | 每个 util 点至少 1 token；更少时 cap 截断，抹掉 R=1～10 token 时唯一可行的抖动逼近 |
| util − u ≥ 10 | 限额 >90 时在过期读数上把 util 压到目标以下，收益最多 9 点 |
| 桶 > 8·share | 区分持续过剩与停顿：开关负载的空闲拍同样 consumed < share、且 util 读数过期偏高；8 拍后延迟读数已归 0，规则自然关闭 |

### 8.3 多进程共享桶

mark 是控制器状态，与 share 一样随 `sm_ctl_load/publish` 存于共享区（布局 v3→v4：
`delta_mark`、`delta_mark_valid`），因为每周期的补桶 winner 可能是不同进程。
`change_token` 返回实际施加的改动（含夹紧）；auto 路由到 AIMD 的周期使 mark 失效
（`g_delta_mark_fresh`），不在过期基线上累加。`test_sm_node_shared [7]`：6 个进程并发

### 8.7 第 2 步（治 u≥50 下调慢、清残余）：否定结论

（这些候选当时以容量上限 7c190ac 为现状；结论针对的是延迟反馈结构本身，对 v15 观测同样成立。）

以 7c190ac 为现状、v14 为验收基线，硬路径全量验收（51 种卡型宽域 + 突降/突增/间歇），
共试 22 个候选，无一能在不新增退步的前提下清掉 8.4 的残余。记录在此，免得重走：

| 方向 | 结果 |
|---|---|
| 饱和（读数 100）按爆冲处理，含/不含池相对下限、含"半个安全乘性下调" | 否决：u≥90 时 util 正常会碰到 100，饱和下调在稳态造出极限环，p95 均值 18.8→25～28，宽域约 5.5 万格超限 |
| 去掉池相对应急下限 `total·err/(u·64)` | 均值全面变好（稳态 13.90、冷启动 17.45、突降 7.24），但宽域 6878 格超限（最差 +15）；间歇残余不减 |
| 温和下调去掉积压衰减 | 均值小幅全面变好（间歇 13.03），但老 3 档 32 格、宽域 1667 格超限 |
| 空闲后 H 拍只降不升（以 bypass 条件判空闲） | 间歇均值 14.1→9.2，但新增 3000～4000 格超限（最差 +66）：bypass 条件在稳态也会因延迟读数偏低而触发 |
| 精确空闲（消耗量 C=0 且 share>0）+ 保持，含/不含 bypass | 去掉 bypass 后宽域约 6 万格超限；保留 bypass 时间歇最差 +83：开 1 停 1、开 2 停 2 这类 100～200 ms 节奏被当成空闲，丢掉了跨拍结转 |

由此得到的认识：

1. **bypass 的主要价值在稳态**：延迟读数偏低且本拍未被节流时它给桶重新赋值，等于顺带清一次积压，
   这在轻负载上很有益（v14 硬路径 15.37 优于软路径 16.69 即来源于此），比它名义上的空闲处理作用更大。
2. **间歇残余是结构性的**：开关周期与"100 ms 控制周期 + 2～4 拍测量延迟"同量级时，控制器无法区分
   "负载在停"与"读数过期"，在现有反馈结构上加规则只会把误差在场景间搬移。
3. 真正的解法需要换反馈信号：以不延迟的精确消耗量（分支 `wip/sm-consumption-observe` 已有跨进程
   精确计量）为主信号重新设计控制器，并同时解决软路径缺少空闲处理的问题。这是重设计，另立项目。

## 9. 计费单位研究：grids 还是 grids×blocks（HAMi-core PR #376）

工具：`library/test/nogpu/charge_unit_study.c` + `kmix_model.h`（不进 CI，构建命令见文件头）。

### 9.1 方法与前提

NVML util 是**忙时间占比**，launch 时并不知道 kernel 会跑多久，所以两种单位都只是代理量；
对控制器真正有意义的是"每个 util 点对应多少 token"（k）在负载 kernel 组合变化时有多稳定——
组合一变，R 就跳。kmix_model.h 用公开规格（SM 数、每 SM 线程、FP16 Tensor 峰值、显存带宽）
和 PyTorch/cuBLAS/FlashAttention 的典型 launch 形状，按 roofline 估算每个 kernel 的忙时间
（建模，非实测），覆盖 T4/RTX3090/A100/L4/RTX4090/H100/B200 和合成未来卡。

### 9.2 开环：k 在 kernel 之间、阶段之间的跳变

- 单个 kernel 之间：grids 约 3600×，threads 约 450～1600×。根源是每线程工作量（A100 上逐元素
  1677 万线程 324 µs，大 GEMM 52 万线程 2.5 ms），threads 只消掉 block 大小这一维。
- 负载阶段之间：

| 切换 | grids | threads |
|---|---|---|
| 训练 前向/反向 ↔ optimizer | 12～52× | **3.4～15×** |
| 推理 prefill ↔ decode | **9～53×** | 10～60× |
| 五个阶段 max/min | 179～278× | 114～299× |

- 两种单位共同的趋势：GPU 越新跳变越大（T4 约 180×、B200 约 280×、合成未来卡约 600×）——
  算力增长而 launch 下限不变。控制器必须扛住越来越大的 R 跳变，与单位无关。

### 9.3 闭环：v15 在阶段交替下（8 款 GPU × 3 组阶段 × 段长 1/3/10/50 周期 × 限额 10～90 × 延迟 2/4 × 两条路径）

| 方案 | 平均 MAE | 比现状差 >2 / 好 >2 | 最差单格 |
|---|---|---|---|
| grids，FACTOR=32（现状） | 26.78 | — | — |
| grids，FACTOR=128 | 24.50 | 652 / 1067 | +38.7 |
| threads，FACTOR=32（= PR #376 的做法） | 45.16 | 2277 / 725 | +80.2 |
| threads，FACTOR=2048 | 29.17 | 1451 / 810 | +23.0 |
| threads，FACTOR=16384～32768 | 23.54～23.59 | 587～689 / 1234～1247 | +37.2 |

### 9.4 结论

1. 计费单位本身的收益约 1 个 MAE 点（约 4%）：grids 只调池子大小已从 26.78 到 24.50，threads 最佳为
   23.54。threads 看起来的大部分优势来自池子（R/pool 落点）而不是单位。
2. 照搬 PR #376（threads + FACTOR 32）在我们的控制器下明显更差：HAMi 自己的控制器靠 g_total 只增
   不减的翻倍兜底，那正是以精度为代价的做法。
3. 两条路线相对现状都有约 600～700 格变差 >2，均非全面占优；且 kernel 参数为建模值。改单位还要改
   所有 launch 钩子、处理 grids×blocks 溢出、重新推导全部池相对常量，代价与 4% 不相称。**暂不跟进。**
4. ~~池子大小（FACTOR）是更便宜也更大的杠杆~~——**已被第 10 节推翻**：kernel 组合交替上的改善全部
   来自桶容量变大（跨阶段结转），同一容量在宽域与负载变化验收上全面退化。threads 在大 FACTOR 下的
   kernel 组合收益同样含这部分容量效应，宽域验收同样会退步。

## 10. FACTOR 研究：否定（2026-10）

FACTOR 只出现在池子大小 `g_total = 每 SM 线程 × SM 数 × FACTOR`，但池子同时是 delta 全部池相对
常量的基准、桶的容量上限、AIMD 的 share 上限。为找出收益来源，候选按可分解的方式设计，在**真实 R
空间**（同一负载、同一 R）对现状 v15（FACTOR 32）验收：

| 候选 | 宽域稳态 MAE 软/硬 | 老 3 档逐格失败 | 突降 | kernel 组合交替 |
|---|---|---|---|---|
| 现状 FACTOR 32 | 15.97 / 14.83 | — | 8.91 | 26.78 |
| A：FACTOR 64（常量与容量） | 17.48 / 16.45 | 约 1 万 | 12.6 | 25.24 |
| A：FACTOR 128 | 19.35 / 18.43 | 1.2～1.6 万 | 16.4 | 24.50 |
| A：FACTOR 256 | 21.31 / 20.39 | 约 2.4 万 | 20.5 | 24.58 |
| B：只放大 delta 池相对常量 ×4（容量不变） | 19.63 / 18.71 | 1.2～1.6 万 | 16.4 | 26.85 |
| C：只放大种子 ×4 | 19.22 / 18.29 | 约 9000 | 16.1 | 26.72 |

结论：kernel 组合交替的改善只出现在 A，B/C 都没有——它来自更大的桶容量把轻阶段攒下的 token 结转到
重阶段，是"跨阶段结转"与"积压灌桶"之间的取舍，而非杠杆；同一容量让宽域、老 3 档与突降全面退化。
**FACTOR 保持 32；delta 常量保持现值。** 若要改善阶段交替，需要能区分"结转"与"灌桶"的机制（例如
以消耗量为主信号的下一代控制器，第 8.7 节），不是调池子大小。

工具：本节数据由临时研究程序在真实 R 空间生成（候选 A/B/C 的定义如上），方法与 `charge_unit_study.c`
相同，基于 `delta_sim.h` 的生产周期与 `kmix_model.h`。

> 注：本节结论"FACTOR 保持 32"是在**按 grid 计费**下得出的。v16（第 11 节）同时把计费改为
> grid×block、FACTOR 改为 256，并用"按实测需求放开 share 上限"取代"放大池子"来覆盖重负载——
> 本节否定的是"单纯放大池子/桶容量"，该结论在 v16 中仍然成立（v16 的桶容量只在 share 超过一个池时才
> 跟随 share，且受实测消耗约束）。

## 11. v16：grid×block 计费 + 按需放开上限（2026-10）

### 11.1 起因：#360 复核发现的三处问题（v15，grid 计费，FACTOR 32）

1. **block 少、单次长的 kernel 冲破限额（#360 本身）**。v15 能稳住的下界约 R/pool ≈ 1e-4。persistent
   kernel（grid = #SM，Hopper/Blackwell 上 cuBLAS/CUTLASS 常用）单次超过约 14 ms、NCCL kernel（8～32
   通道）单次超过 1～5 ms 就落到下界以下——与卡型无关。H100 上 35 ms 的 persistent kernel：限额 10 跑到 24%。
2. **block 多、跑得快的 kernel 被过度限流（反方向）**。share 与桶都被钉在一个池以内，util 上限 = 池 ÷ 每拍
   需求；GPU 越快越严重：B200 训练负载限额 50 只能跑到 26%，逐元素运算为主的阶段只有 5%。
3. **限额 ≥ 93 限不住**：util 读数最多超出 7 点，应急下调（util > 2u）与观测下调（超出 ≥ 10）都不可达。

单独把计费改成 grid×block（任何 FACTOR）只会把真实负载整体平移，两端此消彼长（第 9 节；本轮复测：
HAMi-core #376 的做法 = grid×block + FACTOR 32，被压住的格从 81 变成 449）。必须同时拓宽控制器的窗口。

### 11.2 设计

| 部分 | 内容 | 依据 |
|---|---|---|
| 计费 | 每次 launch 扣 grid×block 线程数（`sm_launch_tokens`，128 位乘、饱和封顶）；graph 成本改为各节点 grid×block 之和 | persistent / NCCL 被抬高 384～512 倍 |
| FACTOR | 32 → 256 | 真实负载组对比 256/512/1024/2048，256 低端最好、其余持平 |
| share 上限 | 可超过一个池，上限 = max(池, 2×上周期实测消耗)，且不低于当前 share，最多 65536 个池（`sm_delta_share_cap`） | 无约束放开时软路径空闲积分把 share 推到上千个池（间歇 783 格）；"往下压"会让停顿后的突发重新爬坡 |
| 桶容量 | share 超过一个池时为 2×share，否则仍为一个池（`sm_delta_bucket_ceiling`） | 常规区间行为与 v15 一致 |
| 观测下调门槛 | 限额 91～95：读数饱和（100）即可触发；限额 ≥ 96 不变 | 去掉 u≥96 的修正：那里 v15 最多超 4 点，修正反成锯齿（p95 +4～+11，124 格） |
| 深 share 积压门槛 | share 超过一个池时为 1.5 倍 share（常规区间仍为 8 倍） | 无门槛时重→轻后超限时长是 v15 的 5 倍；1.9 倍时 2.2 倍；1.5 倍时 0.31 倍 |

增长步长上限改为 max(池, share)/10，让很深的 share 仍能按比例增长；精细常量（种子、boot 跳升、应急下限）仍以池为基准。

多进程共享桶：上限由补桶 winner 在同一选举块内按 `shares[]` 计算并经 change_token 的 CAS 夹紧；
auto 路由到 AIMD 的周期保持池上限（`g_delta_ran`）。共享区布局不变。AIMD 的 share 仍以池为上限，
在新计费下行为会变——AIMD/auto 计划移除，未调整。

## 12. v16.1：按 NVML 新样本估计（RTX 2080 Ti 真机迭代，2026-10）

### 12.1 起因：真机实测到的根因（v15 与 v16 共有，除注明外）

测试平台：RTX 2080 Ti（68 SM × 1024，Turing），驱动 595.84，LD_PRELOAD + HOST 模式；每次运行前清空
`/etc/vgpu-manager /tmp/.sm_node /tmp/.vmem_node /tmp/.vgpu_lock`，并从日志核对实际生效的
`HardCoreSize`/`SoftCoreSize`（第一批矩阵曾因 `vgpu.config` 残留全部跑在 30%，已作废）。主指标是
**吞吐份额**（限流后单位时间完成量 / 不限流时），NVML 读数为辅。

| 现象 | 实测证据 | 根因 |
|---|---|---|
| 2～3 s 周期的极限环（pmon 锯齿） | 进程样本每 ~1000 ms 才更新，到达时已过 56～95 ms；1 s 吞吐标准差 8～17 点 | 控制器每 100 ms 动作，对同一个旧读数连续调 10 次；仿真只建模了 1～4 拍新鲜读数 |
| 限额 ≥90 限不住 | gemm L=90：读数 99、share 为需求 2.3 倍、每拍只降 0.2% | NVML 满载只报 93～99，观测削减门槛 `util-u ≥ 10` 永不触发；仿真里满载读 100 恰好触发 |
| 长 kernel ~17% 下限 | 20 ms kernel 在 L=5/20 都是 16.9% | `change_token` 补给时把透支清零，比一拍 share 还贵的 kernel 每拍必放一次 |
| v16：大需求爬升慢 | elem（每拍需 ~250 池）爬升 7～10 s；软路径 L=80 只有 3～4% | share 低于池每拍 +25%、高于池每拍 +10%（grow_cap） |
| 读数滞后一个窗口 | share 改后的下一个读数仍约一半反映旧 share | 驱动对样本的平滑长于其刷新周期；估计器据此决定不做"跳窗" |
| 低占空比降频 | NVML 稳在 20～21 而吞吐只有 15～16（L=20） | 消费级卡空闲片段降频；控制器在自己的信号上是准的 |

### 12.2 设计（`sm_delta_est_control`，`include/sm_delta.h`）

- **只在新样本到来时动作**：样本时间戳变化即新样本，采样周期在运行时检测，不按卡型设参数。估计窗口至少
  500 ms（快采样卡多个样本按时长平均），样本之间 share 保持。
- **一步估计**：窗口内令牌消耗 C 产生读数 m，则 share = C·u/m —— 这就是该负载、该卡、该频率下"每点利用率
  多少令牌"，无增益参数。窗口内若四分之一以上的活跃拍把桶用空（受限窗口），按"撞到 share 的那些拍"的消耗
  均值、并把读数换算到活跃时间来估计；"活跃"= 有消耗或在等令牌，只有"有令牌却没用"算空闲。
- **按时间戳配对**：16 拍环形记录（墙钟毫秒 + 消耗），按与样本区间 (上个样本, 本样本] 的重叠比例加权，
  不受驱动发布延迟影响。
- **读数为 0**：若窗口大部分拍是饥饿的，util < 1，取 C·u 为下界直接跳；否则是空闲，保持；首个估计之前
  沿用 v16 的增长。
- **四舍五入**（少令牌负载截断会在 99% 目标下把 share 减半），估计可为 0（种子增长兜底，不会卡死）。
- **透支结转**：补给下限 `-max(100 拍 share, 上限)`；桶上限 2 拍 share（`sm_delta_est_bucket_ceiling`）。
- 估计状态是控制器状态，放在 sm_node 共享区（布局 v5，每设备 3 个 128 B cache line，共 6272 B < 8192 B
  预留）；`vgpu.config`（只读挂载的全局配置）未改动。

### 12.8 NVML 查询游标（RTX 3090 真机，2026-10）

**根因**：`nvmlDeviceGetProcessUtilization` / `nvmlDeviceGetProcessesUtilizationInfo` 返回的是
**lastSeenTimeStamp 之后**的利用率。nvml.h（API 13）原文："Set lastSeenTimeStamp to a timeStamp retrieved
from a previous query to read utilization since the previous query"，过滤为严格大于，无新样本返回
`NVML_ERROR_NOT_FOUND`。库本地路径与 Go watcher 都固定传"现在 − 1 s"。RTX 3090（驱动 595.84）每 200 ms 出
一个样本，实测读数 = since 之后所有样本的平均：since = now−0.5 s / 1 s / 4 s 时阶跃响应分别 0.6 / 1 / 4 s
走完；since = 上一个样本的原始微秒时间戳时，每个读数恰好是一个 200 ms 周期（0→48→99）。于是 3090 上每个读数是
1 s 滑动平均，与 12.2 的前提"样本描述它与上一个样本之间的时间"不符。2080 Ti 1 s 才出一个样本，两种查询等价，
所以此前没有暴露。

**修复**（库 `get_gpu_process_from_local_nvml_driver`，Go `watcher.UtilQuerySince` + `smWatcherBatchWithContext`）：
每设备记"已读到的最新样本时间戳"（取所有进程中的最大值，驱动原始微秒）。查询时它若在 (now−1 s, now] 内就用它，
否则（没有、超过 1 s，或时钟回拨到未来）用 now−1 s。窗口始终在 (0, 1 s]：最坏与旧行为相同，采样更快的卡自动
更实时，不按型号写常量。Go 侧游标只存 watcher 进程内存；共享文件的 `LastSeenTimeStamp` 仍写 now−1 s——它兼作
读者的 5 s 存活判定与缓存样本过期线，GPU 空闲时游标不前进，写进去会让读者误判 watcher 已死。指标采集器
（`node_gpu.go`）保持 1 s 平均。

多进程：时间片轮转下每个 200 ms 周期的样本只落在当期运行的进程上（两个进程分时，每批 1 条，比例与吞吐一致），
后续周期的样本必然更新，取最大时间戳不会漏样本。

真机（RTX 3090，硬路径，v16.1 与修复版同脚本；稳态 gemm/elem/tiny/persist/graph × L=20/50/80）：

|---|---|---|
| 稳态 L≤80 吞吐误差 | 1.6–1.8 | 2.0–2.4 |
| 稳态 1 s 波动 sd | 2.6–3.2 | **0.6–0.7** |
| GEMM/elem 3 s 交替 L=20 / 50 / 80（1 s 误差） | 16.2 / 26.7 / 33.8 | **10.3–15.0 / 14.8–15.8 / 19.4–26.4** |
| GEMM 开 5 s / 关 5 s，L=20 / 50 | 9.7 / 17.2 | **1.1–1.7 / 5.5–5.8** |
| GEMM/elem 10 s 交替 L=20 / 50 / 80 | 9.8 / 15.9 / 16.4 | **5.5 / 9.4 / 12.5** |
| 同容器双进程 L=60，GEMM 吞吐 1 s sd（硬 / 软） | 6.4 / 12.9 | **4.4 / 5.5** |
